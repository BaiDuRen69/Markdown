## HTTP 练习题(12 题)

HTTP 是协议,光看概念记不住——得用 `curl` 真实发请求、看报文、对照状态码,才能理解每个细节。这一页给 **12 道 HTTP 协议与 curl 实战题**,分三级—— **基础 6 题** (GET / POST / 状态码 / Header / Cookie / curl 调试)、 **进阶 4 题** (HTTPS / CORS / 缓存 / 认证)、 **实战 2 题** (REST API 设计 / HTTP/2 性能优化)。每题含 **题目、提示、可折叠的参考答案** 。

**使用建议**:打开终端,装好 `curl` (Mac/Linux 自带),把每题命令真实跑一遍。再配合浏览器 F12 的 Network 面板,对照看请求/响应报文——HTTP 是"协议层",必须眼见为实。

## 基础(6 题):请求方法与报文

这一组覆盖日常最高频的 HTTP 操作:发 GET、发 POST、看状态码、读懂 Header、理解 Cookie、用 curl 调试接口。把这 6 题练熟,你排查接口问题不再抓瞎。

### 第 1 题:GET 请求

**题目**:用 curl 发 GET 请求:(a) 取用户列表;(b) 带分页查询参数 `?page=2&limit=20`;(c) 带 Authorization 请求头;(d) 用 `-v` 看完整请求/响应报文。说明 GET 的幂等性——为什么别用 GET 改数据。

**提示**:GET 参数在 URL 查询串;`-H` 加请求头;`-v` verbose 看报文(`>` 是发出的,`<` 是收到的);GET 应幂等(多次执行结果一致),改数据用 POST。

参考答案
```
# GET 用来"取数据",参数放在 URL 查询串里,不安全(别放密码)

# 1. curl 最简单的 GET
curl https://api.example.com/users

# 2. 带查询参数(? 分隔路径和参数,& 分隔多个参数)
curl "https://api.example.com/users?page=2&limit=20"

# 3. 带请求头(比如鉴权 token)
curl -H "Authorization: Bearer eyJhbGc..." \
     https://api.example.com/users/me

# 4. 加 -v 看完整请求/响应报文(调试神器)
curl -v https://api.example.com/users
# > GET /users HTTP/1.1        <- 发出的请求行
# > Host: api.example.com
# >
# < HTTP/1.1 200 OK            <- 收到的响应
# < Content-Type: application/json

# 5. 只看响应头(-I)或只看响应体
curl -I https://api.example.com/users   # 只看响应头
curl -s https://api.example.com/users   # -s 静音,不显示进度

# 幂等性:GET 多次执行结果相同,GET 不应改数据(改数据用 POST)
```

### 第 2 题:POST 请求

**题目**:用 curl 发三种 POST:(a) 提交 JSON(前后端分离标配);(b) 提交表单(登录场景);(c) 上传文件(multipart)。写出对应的原始请求报文。

**提示**:`-X POST` 指定方法;`-H "Content-Type: application/json" -d '{...}'` 发 JSON;`-d "a=1&b=2"` 默认表单类型;`-F "file=@path"` 上传文件。请求体在报文空行之后。

参考答案
```
# POST 用来"提交数据",数据放在请求体里,比 URL 安全(尤其 HTTPS)

# 1. 提交 JSON(最常用,前后端分离标配)
curl -X POST https://api.example.com/users \
     -H "Content-Type: application/json" \
     -d '{"name":"小明","email":"xm@example.com"}'

# 2. 提交表单(application/x-www-form-urlencoded)
curl -X POST https://api.example.com/login \
     -d "username=xm&password=secret"
# 不写 -H,curl 见 -d 默认就是表单类型

# 3. 上传文件(multipart/form-data)
curl -X POST https://api.example.com/upload \
     -F "file=@photo.jpg" \
     -F "title=我的照片"

# 4. 用 --data 用文件内容作为请求体
curl -X POST https://api.example.com/import \
     -H "Content-Type: application/json" \
     --data @users.json

# 对应的原始报文:
# POST /users HTTP/1.1
# Host: api.example.com
# Content-Type: application/json
# Content-Length: 48
#
# {"name":"小明","email":"xm@example.com"}
```

### 第 3 题:状态码

**题目**:说出五大类状态码(1xx-5xx)的含义和代表码;用 curl 只取状态码;列出调试时 200/401/403/404/500/502/504 分别对应什么问题;给出 REST API 的状态码使用惯例。

**提示**:2xx 成功、3xx 重定向、4xx 客户端错、5xx 服务端错。 `curl -o /dev/null -s -w "%{http_code}"` 取状态码。401 未认证、403 无权限、404 不存在、500 后端崩、502/504 网关层错误。

参考答案
```
# 五大类状态码(首位表示类别):
# 1xx 信息:WebSocket 升级、持续上传(很少见)
# 2xx 成功:200 OK / 201 Created / 204 No Content
# 3xx 重定向:301 永久 / 302 临时 / 304 Not Modified(缓存有效)
# 4xx 客户端错:400 参数错 / 401 未认证 / 403 禁止 / 404 不存在 / 429 限流
# 5xx 服务端错:500 内部错 / 502 网关错 / 503 不可用 / 504 网关超时

# 用 curl 只取状态码
curl -o /dev/null -s -w "%{http_code}\n" https://example.com
# 200

# 调试时常见组合:
# 200 + 空 body          接口通了但没数据
# 401                    没带 token 或 token 过期
# 403                    带了 token 但没权限
# 404                    URL 错了 / 资源不存在
# 500                    后端崩了,去看日志
# 502 / 504              Nginx 连不上后端 / 后端超时

# REST API 设计惯例:
# GET    /users        -> 200
# POST   /users        -> 201 (创建成功)
# PUT    /users/42     -> 200
# DELETE /users/42     -> 204 (删除成功,无内容返回)
# 错误统一 -> 4xx,并 body 里给详细信息
```

### 第 4 题:Header 请求头

**题目**:列出 5 个常用请求头(Host / User-Agent / Accept / Authorization / Content-Type)和 5 个常用响应头(Content-Type / Content-Length / Cache-Control / Set-Cookie / Location)的作用。用 curl 自定义请求头、查看所有响应头。

**提示**:请求头是"客户端的自我介绍 + 要求",响应头是"服务器告诉客户端怎么处理";`curl -H "键: 值"` 加请求头;`curl -I` 只看响应头。

参考答案
```
# 请求头:客户端告诉服务器"我是谁、我要什么"
# 响应头:服务器告诉客户端"返回的是什么、怎么处理"

# 常用请求头:
# Host: example.com                    目标域名(虚拟主机靠它区分)
# User-Agent: Mozilla/5.0...           客户端标识(浏览器/爬虫)
# Accept: application/json             想要的响应格式
# Accept-Encoding: gzip                能接受压缩
# Authorization: Bearer xxx            鉴权凭证
# Cookie: session=abc123               会话标识
# Content-Type: application/json       请求体格式
# Origin / Referer                     来源( CORS 用)

# 用 curl 自定义请求头
curl -H "User-Agent: MyBot/1.0" \
     -H "Accept-Language: zh-CN" \
     https://example.com

# 常用响应头:
# Content-Type: application/json; charset=utf-8   返回内容格式
# Content-Length: 1234                            内容字节数
# Content-Encoding: gzip                          压缩方式
# Cache-Control: max-age=3600                     缓存策略
# Set-Cookie: session=abc; HttpOnly; Secure       下发 Cookie
# Location: https://...                           重定向目标(配合 3xx)
# Access-Control-Allow-Origin: *                  CORS 允许跨域

# 看所有响应头
curl -I https://example.com
```

### 第 5 题:Cookie 与会话

**题目**:说明 Set-Cookie 响应头的各属性(Path / HttpOnly / Secure / SameSite / Max-Age)分别防什么攻击;用 curl 模拟登录后保持会话(`-c` 存 cookie,`-b` 带 cookie);区分 Cookie、Session、Token 三种方案。

**提示**:`HttpOnly` 防 XSS 偷 cookie、 `Secure` 防明文传输、 `SameSite` 防 CSRF;`curl -c file` 存、 `-b file` 带;Cookie 是存储机制,Session 服务端有状态,Token 无状态自带签名。

参考答案
```
# Cookie 是服务器下发、浏览器自动带上的"小卡片",用来维持会话

# 1. 服务器通过 Set-Cookie 响应头下发
# HTTP/1.1 200 OK
# Set-Cookie: session=abc123; Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=3600

# 关键属性:
# Path=/                生效路径(/ 全站)
# HttpOnly              JS 读不到,防 XSS 偷 Cookie(重要!)
# Secure                只在 HTTPS 下发送
# SameSite=Lax/Strict   防 CSRF(限制跨站带 Cookie)
# Max-Age=3600          有效期 3600 秒(过期浏览器自动删)

# 2. 用 curl 模拟"登录后保持会话"
# 把服务器下的 Cookie 存到文件
curl -c cookies.txt -X POST https://api.example.com/login -d "user=xm&pass=..."

# 后续请求带着 Cookie(从文件读)
curl -b cookies.txt https://api.example.com/users/me

# 3. Session vs Cookie vs Token
# Cookie:   浏览器存储机制,什么都可放(会话 id/偏好)
# Session:  服务端存会话,Cookie 里只放 session id(服务端有状态)
# Token(JWT):服务端无状态,客户端自带签名 token(放 Authorization 头更安全)

# 调试技巧:浏览器 F12 → Application → Cookies 看当前站点的所有 Cookie
```

### 第 6 题:curl 调试技巧

**题目**:演示 curl 常用技巧:(a) `-v` 看报文;(b) `-i` 看响应头+体;(c) `-L` 跟随重定向;(d) `-o/-O` 下载;(e) `-w` 输出 DNS/连接/总耗时;(f) `--resolve` 强制域名解析到指定 IP(测灰度)。

**提示**:`-v` 调试看报文、 `-L` 自动跟跳转、 `-w "%{time_total}"` 量化性能、 `--resolve 域名:端口:IP` 不改 hosts 就能测指定服务器。

参考答案
```
# curl 是 HTTP 调试最常用的命令行工具

# 1. -v 看完整报文(请求+响应,带 > < 前缀)
curl -v https://api.example.com/users
# > GET /users HTTP/1.1          (发出的)
# < HTTP/1.1 200 OK              (收到的)

# 2. -i 把响应头和响应体一起显示
curl -i https://api.example.com/users

# 3. -o 下载到文件,-O 用原文件名
curl -o photo.jpg https://example.com/img.jpg
curl -O https://example.com/report.pdf

# 4. -L 自动跟随重定向(默认不跟)
curl -L http://example.com        # 跟到 https
# 看完整重定向链
curl -L -v http://example.com 2>&1 | grep -E "Location|HTTP/"

# 5. -X 指定方法,-d 发请求体
curl -X DELETE https://api.example.com/users/42
curl -X PUT -H "Content-Type: application/json" \
     -d '{"name":"new"}' https://api.example.com/users/42

# 6. -w 输出耗时(性能排查)
curl -o /dev/null -s -w \
  "DNS:%{time_namelookup} 连接:%{time_connect} 总:%{time_total}\n" \
  https://example.com
# DNS:0.012 连接:0.045 总:0.234

# 7. --resolve 强制把域名解析到指定 IP(测灰度发布)
curl --resolve api.example.com:443:1.2.3.4 https://api.example.com
```

## 进阶(4 题):安全与缓存

这一组是 Web 工程师绕不开的主题:HTTPS 加密、CORS 跨域、HTTP 缓存、认证方案。理解它们,你就能排查"接口跨域报错""登录态丢失""资源不缓存"等老大难问题。

### 第 7 题:HTTPS 原理

**题目**:简述 HTTPS 握手过程(加密/认证/完整性怎么实现);用 openssl 看证书的 subject、有效期、颁发机构;curl 跳过证书验证(`-k`)和强制指定 TLS 版本;测试 HTTP/2 支持。

**提示**:HTTPS = HTTP + TLS;握手交换会话密钥,之后对称加密;`openssl s_client` 看证书;`curl -k` 忽略证书(仅调试用);`--tlsv1.3` 强制 TLS1.3;`--http2` 测 h2。

参考答案
```
# HTTPS = HTTP + TLS/SSL 加密
# 解决三大问题:加密(防窃听)、认证(防冒充)、完整性(防篡改)

# 1. 握手简化过程(HTTPS 比 HTTP 多 1-2 个 RTT):
# 客户端 ---ClientHello--->            服务器
#         <---ServerHello+证书+公钥---
# 客户端验证证书(签名链有效、未过期、域名匹配)
# 客户端用公钥加密一个"会话密钥"发给服务器
# 双方用会话密钥对称加密后续数据(AES,快)

# 2. 用 openssl 看证书详情
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null \
  | openssl x509 -noout -subject -dates -issuer
# subject=C = US, CN = example.com
# notBefore=Aug  1 00:00:00 2026 GMT
# notAfter=Oct 31 23:59:59 2026 GMT    <- 到期日
# issuer=C = US, O = Let's Encrypt     <- 颁发机构

# 3. curl 不验证证书(调试自签证书,生产别用!)
curl -k https://self-signed.example.com

# 4. 强制指定 TLS 版本
curl --tlsv1.2 https://example.com
curl --tlsv1.3 https://example.com   # 现代标准,握手更快

# 5. 测 HTTP/2 / HTTP/3 支持
curl -I --http2 https://example.com   # 看响应里有没有 HTTP/2
```

### 第 8 题:CORS 跨域

**题目**:解释同源策略(协议+域名+端口);区分简单请求和需要预检(PREFLIGHT)的请求;写出预检响应需要的 4 个 CORS 头;给 Nginx 写一段 CORS 配置;用 curl 模拟跨域测试。

**提示**:简单请求直接发;PUT/DELETE/自定义头/非标准 Content-Type 触发 OPTIONS 预检;响应要 `Access-Control-Allow-Origin/Methods/Headers/Max-Age`;`curl -H "Origin: xxx" -I URL` 测跨域头。

参考答案
```
# CORS(Cross-Origin Resource Sharing)跨域资源共享
# 浏览器同源策略:协议+域名+端口 三者全相同才是"同源"
# 跨域请求浏览器会拦截,除非响应里有正确的 CORS 头

# 1. 简单请求(GET/POST,标准 Content-Type)
#    浏览器直接发,服务器响应要带:
# Access-Control-Allow-Origin: https://app.example.com   # 允许的来源
# Access-Control-Allow-Credentials: true                 # 允许带 Cookie

# 2. 预检请求(PREFLIGHT):复杂请求前浏览器先发 OPTIONS
#    触发条件:PUT/DELETE 方法,或自定义头,或非标准 Content-Type
#    浏览器:OPTIONS /api/users + Origin + Access-Control-Request-*
#    服务器响应:
# Access-Control-Allow-Origin: https://app.example.com
# Access-Control-Allow-Methods: GET, POST, PUT, DELETE
# Access-Control-Allow-Headers: Content-Type, Authorization
# Access-Control-Max-Age: 86400                            # 预检结果缓存 1 天

# 3. Nginx 配置 CORS 示例
location /api/ {
    add_header Access-Control-Allow-Origin "https://app.example.com" always;
    add_header Access-Control-Allow-Methods "GET, POST, PUT, DELETE, OPTIONS" always;
    add_header Access-Control-Allow-Headers "Content-Type, Authorization" always;
    if ($request_method = OPTIONS) {
        return 204;       # 预检请求直接返回空
    }
    proxy_pass http://backend;
}

# 4. 用 curl 模拟跨域请求测试
curl -H "Origin: https://app.example.com" -I https://api.example.com/data
# 看响应里有没有 Access-Control-Allow-Origin 头
```

### 第 9 题:HTTP 缓存

**题目**:区分强缓存和协商缓存;列出 `Cache-Control` 的常用值(max-age / public / private / no-cache / no-store);说明 ETag/If-None-Match 协商缓存怎么返回 304;给 Nginx 静态资源写"长缓存+指纹化"配置。

**提示**:强缓存(Cache-Control: max-age)不发请求;协商缓存(ETag)发请求,服务器说没改返回 304(空 body 省带宽);指纹化文件名配合 `immutable` 连 304 都不发,是终极优化。

参考答案
```
# HTTP 缓存分两类:强缓存(不发请求)、协商缓存(发请求问服务器)

# === 强缓存(直接用本地副本,不发请求) ===
# Cache-Control: max-age=3600          缓存 3600 秒(优先级最高)
# Cache-Control: public                中间 CDN 也能缓存
# Cache-Control: private               只能浏览器缓存(用户数据)
# Cache-Control: no-cache              强制每次问服务器(走协商)
# Cache-Control: no-store              完全不存(敏感数据)
# Expires: Wed, 05 Aug 2026 12:00:00 GMT   老版本,绝对过期时间

# === 协商缓存(发请求,服务器说没改就返回 304) ===
# 服务器下发:ETag: "abc123"            内容指纹
# 下次请求带上:If-None-Match: "abc123"
# 服务器对比:没变 -> 304 Not Modified(空 body,省带宽)
#             变了 -> 200 + 新内容

# 老一套:Last-Modified / If-Modified-Since(精度到秒,不如 ETag)

# Nginx 静态资源缓存配置(组合用法)
location ~* \.(css|js|jpg)$ {
    etag on;                              # 自动生成 ETag
    expires 1y;                           # 强缓存 1 年
    add_header Cache-Control "public, immutable";
    # immutable:指纹化的文件名永远不变,连 304 都不发(终极优化)
}

# 验证缓存是否生效
curl -I https://example.com/style.css
# 看到:Cache-Control、ETag、Expires 都对上了
```

### 第 10 题:认证方案

**题目**:演示四种认证:(a) Basic Auth;(b) Session + Cookie(`-c/-b`);(c) JWT Token(Authorization 头);(d) OAuth 2.0(第三方登录流程)。解码 JWT 的 payload 看内容,说明 JWT 为什么不能放敏感信息。

**提示**:Basic 每次带密码;base64 不加密;Session 服务端有状态;JWT 无状态自带签名,payload 是 base64 不是加密,别放密码;OAuth 适合"用 GitHub 登录"这种第三方授权。

参考答案
```
# 四种主流认证方式

# 1. Basic Auth:用户名密码每次都带(不安全,基本不用)
curl -u user:pass https://api.example.com/data
# 报文:Authorization: Basic dXNlcjpwYXNz==  (base64 编码)

# 2. Session + Cookie:登录后服务器发 session id
#    服务器存 session(内存/Redis),有状态
curl -c cookies.txt -X POST https://api.example.com/login -d "user=xm&pass=..."
curl -b cookies.txt https://api.example.com/users/me

# 3. Token(JWT):登录后服务器发 token,无状态
#    token 放 Authorization 头,服务器验签不查库
curl -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIs..." \
     https://api.example.com/users/me

# JWT 三段:header.payload.signature
# 解码看 payload(只是 base64,不加密,别放敏感信息)
echo "eyJzdWIiOiIxMjMifQ" | base64 -d
# {"sub":"123"}

# 4. OAuth 2.0:第三方登录("用 GitHub 登录")
#    流程:跳授权页 -> 用户同意 -> 拿 code -> 换 access_token -> 调 API
#    适合开放平台,自己业务一般用 JWT

# 实战:用 GitHub Personal Access Token 调 API
curl -H "Authorization: token ghp_xxx" \
     https://api.github.com/user
```

## 实战(2 题):设计与优化

这两题考查综合能力:设计一套规范的 REST API,和用 HTTP/2 等手段优化网站性能。这是后端架构和前端工程的通用话题。

### 第 11 题:REST API 设计

**题目**:为"用户"资源设计一套标准 REST API:列出 GET/POST/PUT/PATCH/DELETE 各对应的 URL、方法语义、成功状态码;设计嵌套资源(/users/42/orders)、筛选排序分页的查询参数;给出一套统一的成功/错误响应 JSON 格式;说明怎么做版本控制。

**提示**:URL 表达"是什么资源",HTTP 方法表达"做什么";状态码 200/201/200/200/204;嵌套用 `/users/{id}/orders`;筛选排序分页用查询参数;错误用 4xx + body 详情;版本在 URL 里 `/api/v1/` 。

参考答案
```
# REST:用 HTTP 方法表达"对资源做什么",URL 表达"是什么资源"

# 用户资源的标准 REST 设计:
# GET    /users          获取用户列表    200
```

### 第 12 题:性能优化(HTTP/2)

**题目**:说明 HTTP/1.1 的痛点(队头阻塞、连接数限制)和 HTTP/2 的四大改进(多路复用、二进制分帧、头部压缩、服务器推送);在 Nginx 开启 HTTP/2 并验证;列出 HTTP/3 的改进(QUIC、0-RTT);给出一份通用 HTTP 性能优化清单。

**提示**:HTTP/2 一个连接并发多请求解决队头阻塞;`listen 443 ssl http2` 开启,浏览器 F12 Network 看 Protocol=h2;HTTP/3 基于 UDP 的 QUIC,握手更快;优化清单:HTTPS+H2、压缩、长缓存+指纹、CDN、懒加载。

参考答案
```
# 从 HTTP/1.1 到 HTTP/2 到 HTTP/3 的性能演进

# === HTTP/1.1 的痛点 ===
# 1. 队头阻塞:一个请求慢,后面的全排队
# 2. 文本协议:解析慢,体积大
# 3. 连接数限制:浏览器对同域名最多 6 个并发
# 优化套路:域名分片、雪碧图、合并文件(都是 hack)

# === HTTP/2 的改进 ===
# 1. 多路复用:一个 TCP 连接并发多个请求(队头阻塞解决)
# 2. 二进制分帧:解析快、体积小
# 3. 头部压缩:HPACK 算法,重复头只传一次
# 4. 服务器推送:服务器主动推 CSS/JS(现已不推荐,改用 <link preload>)

# 1. 服务器开启 HTTP/2(Nginx 一行)
# listen 443 ssl http2;
# 验证:浏览器 F12 → Network → Protocol 列显示 h2

# 2. 用 curl 测试
curl -I --http2 https://example.com
# 响应里 HTTP/2 200

# === HTTP/3(基于 QUIC,UDP) ===
# 解决了 TCP 层的队头阻塞,握手 0-RTT(更快)
# listen 443 quic reuseport;  # Nginx 1.25+ 支持
# curl --http3 https://example.com   # curl 7.66+

# === 通用性能优化清单 ===
# 1. 用 HTTPS + HTTP/2(必须,免费的大提升)
# 2. 静态资源开 gzip / brotli 压缩(体积砍 70%)
# 3. 长缓存 + 文件指纹(Cache-Control: max-age=31536000, immutable)
# 4. 用 CDN 就近分发(降低 RTT)
# 5. 合并关键 CSS、懒加载图片、<link rel="preconnect"> 提前建连
# 6. 用 Lighthouse 跑一遍(F12 → Lighthouse),按建议优化
```

## 练习建议

**用 curl 真实发请求** 。HTTP 是协议,光看书没用——必须用 curl 真发请求,看返回的状态码、Header、报文体。每题的命令都亲手敲一遍,改改参数(URL、Header、方法)看响应变化。

**配合浏览器 F12**:打开任意网站,Network 面板能看到所有请求的完整报文;Application 面板能看 Cookie 和 LocalStorage;Lighthouse 能跑性能报告。把命令行和图形界面结合起来,理解会深得多。

**试着扩展**:做完第 1-6 题,用 curl 调一个真实公共 API(GitHub、知乎、天气);做完第 8 题 CORS,自己起两个端口不同的本地服务复现跨域报错并解决;做完第 12 题,用 Lighthouse 跑自己网站的评分并按建议优化。
