> 本表不记录任何截图里的勾选状态，39 项统一解读；实际该勾哪些，以你自己的用途为准。

## 先记住三件事

1. **「读」和「写」是两个世界。** `read` 通常只是看，`write` 才真的会改动仓库。绝大多数事故都来自顺手多给了 `write`。
2. **光看单项风险会低估危险。** 权限要组合起来看：单给一项可能没事，两项一起就能串成一条完整攻击链（见文末「组合坑」）。
3. **默认给只读，只给一个用途。** 一个令牌只干一件事，明确需要写才开 `write`，用完定期复查、轮换。

## 风险等级怎么分

| 等级 | 一句话 | 典型后果 |
|---|---|---|
| **极高** | 一次误授就可能造成不可逆损失 | 删库、源码或未公开漏洞泄露、长期静默外带凭据、拆掉发布审批 |
| **高** | 能改代码、改 CI、绕过审批 | 注入恶意代码、伪造检查通过、发布未经批准的版本 |
| **中高** | 接近「高」，但通常要配合别的权限才致命 | 伪造状态、放行含密钥的提交 |
| **中** | 能掩盖告警、伪造状态、改配置 | 干扰审计与判断，本身一般不直接毁数据 |
| **中低** | 接近「低」，但有一点写入面 | 刷假指标、改动社区内容 |
| **低** | 只读，或只影响社区内容 | 信息可见，几乎无法造成破坏 |

> 原文里的「中高」「低中」就是夹在相邻两档之间的中间档，这里统一写成「中高 / 中低」方便对照。

## 一、仓库治理与集成（7 项）

> **这一组管「仓库本身」**：谁能进来、叫什么名字、能不能删、事件往哪发。整组是最高危区域，绝大多数自动化脚本一项都不用给。

| 权限 | 它管什么 | 给了之后能做什么 | 风险 | 什么时候才需要 |
|---|---|---|---|---|
| **Metadata**（元数据） | 仓库名称、描述、协作者名单、能否被搜索到等基础信息 | **只读**。用来「找到」仓库并读基本信息，不给代码、不给任何修改能力。**所有令牌都必须带**，否则连仓库都定位不到 | 低 | 任何令牌，强制必选 |
| **Administration**（仓库管理） | 仓库设置页里的全部内容：协作者与团队、可见性、转让、删除、创建 | `read` 只能看设置；`write` 可以直接**删库、把私有仓库改成公开、把仓库转给别人、随意加协作者** | 极高 | 只做仓库迁移、归档、批量治理时；日常自动化基本不该给 |
| **Repository creation**（创建仓库） | 2026 年 10 月新增，只授权「在这个账户名下新建仓库」，含用模板建库、fork、通过 GraphQL 接口建库 | 批量建新库；建库人自动获得新库的访问权限，所以能进自己建的库。**不附带**删除、转让他人仓库的能力 | 高 | 脚手架批量初始化。官方建议：只想建库就用它替代 Administration，免得顺手把删库权限也送出去 |
| **Repository license policy**（许可证合规策略） | 仓库级的开源许可证合规规则，配合 2026 年 License Compliance 公开预览使用。说白了就是「哪些许可证的依赖允许进代码，哪些要拦」 | 切换策略的执行模式：**Active**（真的拦截）／**Evaluate**（只评估记录不拦），以及管理例外白名单。有写权限就能把「阻断合并」降级成「仅提示」，让违规依赖悄悄进主干 | 中高 | OSPO（开源项目办公室）或法务做合规治理 |
| **GitHub App installation repository access**（App 安装范围） | 2026 年 10 月新增的 `installation_repositories:write`，控制「某个 GitHub App 能看到本组织的哪些仓库」 | 把该仓库**加入或移出组织内任意 App 的安装范围** | 极高 | 自动化管理 App 的可见仓库范围。滥用后果：给恶意 App 开门拿代码，或把安全扫描 App 踢出去让防护凭空消失 |
| **Custom properties**（自定义属性） | 组织给仓库打的自定义标签，例如「业务等级＝P0」「数据分级＝敏感」 | 读写这些标签。看似无害，但很多 ruleset（规则集）和保护策略是按属性生效的——改一个标签就可能让仓库自动脱离保护 | 中 | 资产分类、合规分级、按标签路由策略 |
| **Webhooks**（事件回调） | 仓库的 webhook 配置与投递记录。仓库发生 push、PR 等事件时，GitHub 会往填写的网址发一条通知 | `read` 能看到回调地址与密钥配置；`write` 能增删改回调、重放历史投递 | 极高 | CI 触发、第三方集成。危险点：把地址改成自己控制的外部服务器，就能**长期、安静地把仓库事件持续外发**，极难察觉 |

## 二、代码与协作（6 项）

> **这一组管「代码本身和日常协作」**，也是自动化最常申请的一组。注意：`Contents` 和 `Pull requests` 一旦给到写权限，就等于把改代码的权力交出去了。

| 权限 | 它管什么 | 给了之后能做什么 | 风险 | 什么时候才需要 |
|---|---|---|---|---|
| **Contents**（仓库内容） | 文件、提交、分支、tag、release；也是通过 HTTPS 用 Git 克隆／推送代码时必需的权限 | `read` 读全部源码；`write` 能 **push 代码、删分支、建 release、直接改文件** | 高 | CI 克隆代码、发版脚本、机器人批量改文件。只想读代码时给 `read` 就够，别顺手开 `write` |
| **Pull requests**（合并请求） | PR 本身、评审、评论、评审人、合并动作 | `read` 看 PR 内容；`write` 能开／关 PR、**合并 PR**、提交评审意见 | 高 | 自动修复机器人、自动提发版 PR。危险点：配合写权限可做到自己提、自己批、自己合，绕过人工评审 |
| **Issues**（问题单） | issue、评论、label、里程碑、负责人 | `read` 查看；`write` 读写 issue 从创建到关闭的整个生命周期 | 中 | 客服机器人、问题分流（triage）、自动打标签 |
| **Commit statuses**（提交状态） | 挂在每个提交上的状态标记：pending（进行中）／success（成功）／error／failure（失败） | `read` 看状态；`write` 能给**任意提交**打上「成功」 | 中高 | CI 上报构建结果。危险点：分支保护常要求「检查必须通过」，伪造一个 success 就能让没跑过测试的代码过关。注意这只覆盖 Commit Status API，Checks API（另一套更细的检查接口）不在这项范围内 |
| **Discussions**（讨论区） | 讨论帖、评论、采纳的答案、内容审核 | `read` 查看；`write` 可读写、删除、置顶讨论 | 中低 | 社区运营机器人 |
| **Merge queues**（合并队列） | 合并队列里排队等待合入主干的 PR 条目。队列会把多个 PR 排成一队，逐个验证后再合入 | `read` 查看队列；`write` 可插队、移除队列项 | 中 | 大规模主干开发时的合并队列运维 |

## 三、CI/CD、构建与供应链（8 项）

> **这一组管「自动构建和发布流水线」**。最容易被低估的是 `Workflows`：改 workflow 文件，就等于改 CI 里要执行的命令。

| 权限 | 它管什么 | 给了之后能做什么 | 风险 | 什么时候才需要 |
|---|---|---|---|---|
| **Actions**（工作流运行） | 工作流的运行记录、job（任务）、artifact（构建产物）、cache（缓存）、self-hosted runner（自建运行器） | `read` 看日志和产物；`write` 能手动触发任意 `workflow_dispatch` 工作流、取消运行、删除产物与缓存、管理自建运行器 | 高 | 触发部署流水线、清理缓存。`workflow_dispatch` 指 Actions 里「允许手动点击运行」的触发方式 |
| **Workflows**（工作流定义） | **只有写权限**，专管 `.github/workflows/` 目录下的 CI 定义文件 | 改 CI 到底跑什么。重点：**光有 `Contents: write` 还不够，改 workflow 文件必须额外勾这一项** | 极高 | 自动维护 workflow。滥用后果：往 CI 里塞一条命令 = 在构建机上执行任意命令，进而拿走该流水线能碰到的全部密钥 |
| **Deployments**（部署记录） | 部署记录与部署状态：哪次发布到了哪个环境、成功还是失败 | `read` 查看；`write` 能创建部署记录、更新状态、触发关联集成 | 中高 | CD（持续部署）系统回写状态。危险点：可伪造「已成功部署」，干扰审计和回滚判断 |
| **Environments**（部署环境） | 环境（如 production 生产／staging 预发）、环境保护规则，以及挂在环境上的 secrets 和 variables | `read` 查看；`write` 能增删环境、改保护规则，包括审批人、允许部署的分支、等待时间 | 极高 | 环境自助管理。危险点：**把生产环境的发布审批闸门直接拆掉**，之后发布不再需要人批准 |
| **Pages**（站点） | GitHub Pages 的配置、构建、自定义域名 | `read` 查看；`write` 能改站点内容、触发构建、改绑定的自定义域 | 中高 | 文档站发布。危险点：改域名可用于钓鱼或子域接管（把原本指向你文档的域名指到攻击者页面） |
| **Artifact metadata**（产物元数据） | 构建产物的存储／部署记录（2026 年 1 月正式可用，GA） | `read` 查元数据；`write` 创建记录 | 中 | 审计、SBOM（软件物料清单）、制品溯源。危险点：伪造记录会干扰「这个包到底从哪来」的追踪 |
| **Attestations**（制品证明） | 制品来源／构建证明（provenance），用来证明「这个包确实由某次可信构建产出」 | `read` 验证证明；`write` 生成证明 | 高 | 供应链签名。危险点：**伪造证明能让一个恶意构建看起来完全可信**，下游校验会被骗过去 |
| **Code quality**（代码质量结果） | 代码质量、测试覆盖率等 findings（检查结果） | `read` 查报告；`write` 上传或管理结果数据 | 中低 | CI 上传覆盖率报告。危险点：可以刷出漂亮的假指标 |

## 四、密钥与配置（6 项）

> **这一组全是「给自动化喂凭据」的入口。** 共同规律：`Secrets` 系列**只写不读**（接口不返回明文），`Variables` 系列**值直接可见**。
> 所以真正的风险不是「读到密钥」，而是「能写入／使用密钥」——尤其是配合 `Workflows` 或 `Contents` 把密钥用出去。

| 权限 | 它管什么 | 给了之后能做什么 | 风险 | 什么时候才需要 |
|---|---|---|---|---|
| **Secrets**（Actions 密钥） | 仓库级 Actions 加密密钥 | 只有 `write`：增、改、删。接口**不会返回明文**，所以勾了它也读不出已有密钥的值 | 高 | 轮换 CI 凭据。危险点：能写入新密钥，再配合 Workflows 改一条工作流把密钥发到外部，等于间接拿到凭据 |
| **Variables**（Actions 变量） | 仓库级 Actions 非密变量 | `read`／`write` 均可，**值可以直接看到** | 中 | 配置注入。注意变量里常放内网地址、账号名、环境标识，本身就能当情报用 |
| **Dependabot secrets** | Dependabot（自动更新依赖的机器人）访问私有制品库时用的密钥 | 只有 `write`：增、改、删 | 中高 | 让 Dependabot 能连上私有 registry（私有软件包仓库） |
| **Codespaces secrets** | 注入云开发环境（Codespaces）的加密密钥，只有写权限 | 增、改、删；在 codespace 内部可以取用这些值 | 高 | 给云端开发环境发凭据 |
| **Agent secrets** | Copilot coding agent（GitHub 的 AI 编码代理）专用加密密钥 | 增、改、删；代理执行任务时可以读取 | 高 | 给 AI 代理配私有制品库凭证或其他令牌 |
| **Agent variables** | Copilot coding agent 的非密变量 | `read`／`write` 均可，值可见 | 中 | 给 AI 代理传配置参数 |

## 五、安全告警与合规（7 项）

> **这一组的写权限几乎都指向同一件事：把真实问题标记成「没问题」。** 给之前先问一句——这个令牌真的需要「关闭告警」吗？只读通常就够了。

| 权限 | 它管什么 | 给了之后能做什么 | 风险 | 什么时候才需要 |
|---|---|---|---|---|
| **Code scanning alerts**（代码扫描告警） | CodeQL 等代码扫描工具报出的安全告警 | `read` 查看；`write` 能关闭或重开告警 | 中高 | 安全平台同步告警状态。危险点：把真实漏洞的告警关掉，问题就「消失」在报表里了 |
| **Dependabot alerts**（依赖漏洞告警） | 依赖包被曝出已知漏洞时的告警 | `read` 查看；`write` 能 dismiss（以「不适用／不修」等理由忽略掉） | 中高 | 漏洞治理。危险点：掩盖未修漏洞 |
| **Secret scanning alerts**（密钥泄露告警） | 历史提交中检测到的凭据（API key、密码等）泄露告警 | `read` 查看；`write` 能关闭，理由可填「误报」「已轮换」等 | 高 | 泄露应急响应。危险点：滥用会隐藏真实泄露，让还没轮换的密钥继续有效 |
| **Secret scanning alert dismissal requests**（关闭告警审批请求） | 开发者提交的「我想关闭这条告警」审批申请 | `read` 查看申请；`write` 能批准或拒绝。**批准等于把真实密钥标记为误报** | 高 | 把告警关闭权下放给团队时使用的审批流 |
| **Secret scanning push protection bypass requests**（推送保护绕过申请） | push protection（推送保护）拦下含密钥的提交后，开发者提出的「放行」申请 | `read` 查看；`write` 能批准，允许把含密钥的提交推入库 | 高 | 紧急放行。危险点：等于给泄露开绿灯，密钥会实实在在写进仓库历史 |
| **Repository security advisories**（仓库安全公告） | 仓库里的私密漏洞公告，含草稿、发布、申请 CVE 编号 | `read` 能看到**尚未公开的 0-day 漏洞细节**；`write` 能起草公告或提前公开发布 | 极高 | 漏洞披露协调。危险点：泄露还未修复的漏洞细节，等于提前把攻击方法交出去 |
| **License compliance alerts**（许可证合规告警） | 依赖许可证违规告警（新增项，官方权限级别文档尚未列全） | `read` 查看；`write` 处置违规依赖告警、管理例外 | 中 | 法务合规。危险点：可降低甚至取消阻断强度 |

## 六、AI 代理与云开发环境（5 项）

> **这一组管「AI 帮你写代码」和「云端开发环境」**。核心一句话：`Agent tasks: write` 的效果等同于「让 AI 拿着你的身份去改仓库」。

| 权限 | 它管什么 | 给了之后能做什么 | 风险 | 什么时候才需要 |
|---|---|---|---|---|
| **Agent tasks**（AI 代理任务） | Copilot cloud agent（云端 AI 编码代理）的任务。目前为公开预览，仅用户令牌可用，且需要 Copilot Business／Enterprise 订阅 | `read` 列出任务；`write` 能**启动任务，让 agent 改代码、开 PR** | 高 | 批量派发 AI 编码任务。等于让 AI 以你的身份动仓库 |
| **Copilot agent settings**（AI 代理设置） | 只读查看 coding agent 的配置 | 只能看启用状态和配置项，**不能改** | 低 | 合规盘点 |
| **Codespaces**（云开发环境） | 仓库下的 codespace 实例（打开就能写代码的云端环境） | 创建、启动／停止、删除**自己**的环境 | 中 | 云端开发。注意会产生计算费用，且环境内能访问仓库代码 |
| **Codespaces lifecycle admin**（环境生命周期管理） | 仓库内**所有** codespace 的生命周期，不限于自己的 | 强制停止或删除他人的环境 | 中 | 成本治理。危险点：能毁掉别人没提交的工作 |
| **Codespaces metadata**（环境元数据） | 只读：环境名称、状态、机型、所有者 | 仅查看 | 低 | 资产盘点 |

## 术语小词典

| 术语 | 大白话 |
|---|---|
| `read` / `write` | 只读 / 可写。权限下拉框里的两档，写权限包含改动能力 |
| fork | 把别人的仓库复制一份到自己账号下 |
| GraphQL | GitHub 提供的另一种查询／操作接口，和常见的 REST API 作用类似，写法不同 |
| OSPO | Open Source Program Office，开源项目办公室，负责公司级开源合规治理 |
| ruleset | 规则集，一组强制生效的分支保护规则，可按仓库属性自动套用 |
| `workflow_dispatch` | Actions 中「允许手动点击运行」的触发方式 |
| runner | 真正执行 CI 任务的机器，可以是 GitHub 托管，也可以是自己搭的（self-hosted） |
| artifact / cache | 构建产物（打出来的包）／构建缓存（加速用的中间文件） |
| GA | Generally Available，正式可用，不再是预览版 |
| SBOM | Software Bill of Materials，软件物料清单，列出一个软件里所有依赖组件 |
| provenance / Attestation | 构建来源记录 / 来源证明，用来回答「这个包是谁、在哪次构建里产出的」 |
| registry | 软件包仓库，存放 npm、Maven、Docker 镜像等依赖的地方 |
| triage | 问题分流：给新 issue 分类、打标签、指派负责人 |
| dismiss | 以「误报／不修／不适用」为由忽略并关闭一条告警 |
| 0-day | 尚未公开、官方还没来得及修的漏洞 |
| CVE | 公开漏洞的统一编号，方便各方引用同一问题 |
| push protection | 推送保护：提交里检测到密钥时直接拦下，不让推入库 |
| tag / release | 版本标签 / 发行版（带说明和打包文件的正式版本） |
| staging / production | 预发环境 / 生产环境 |
| private → public | 把私有仓库改成公开，通常不可逆（源码一旦被抓取就收不回来） |
| Commit Status API vs Checks API | 两套上报检查结果的接口：前者只挂一个简单的「成功／失败」状态，后者能给出详细步骤和日志；权限是分开算的 |

## 最容易踩的 4 个组合坑

> 单项看都「还好」，串起来才是完整攻击链。以下是实践提醒，不是官方条款。

1. **Workflows ＋ Secrets**：改 CI 定义 ＋ 能写密钥 ＝ 在工作流里加一条命令把凭据发到外部，间接拿到明文。
2. **Commit statuses ＋ Contents**：给任意提交打「成功」 ＋ 直接 push ＝ 没跑测试的代码也能通过分支保护合进主干。
3. **Environments ＋ Actions**：拆掉生产审批闸门 ＋ 触发部署流水线 ＝ 无人批准的情况下把任意版本发到生产。
4. **Pull requests ＋ Contents**：自己开 PR、自己批、自己合 ＝ 人工评审形同虚设。

## 按用途配最小权限

> 以下是常见用途的起步配置，按实际需要再加项；能用 `read` 就别用 `write`。

| 用途 | 起步配置 |
|---|---|
| 只克隆／读代码 | Metadata ＋ `Contents: read` |
| CI 上报构建状态 | Metadata ＋ `Commit statuses: write` |
| 批量建新仓库 | Metadata ＋ Repository creation（**不要**给 Administration） |
| 社区／客服机器人 | Metadata ＋ Issues，需要讨论区再加 Discussions |
| 文档站发布 | Metadata ＋ Pages（配合 Contents，视脚本而定） |
| 漏洞告警只读盘点 | Metadata ＋ 对应告警项的 `read` |

**通用原则**：默认只读；一个令牌只服务一个用途；`write` 只在明确知道要改什么时才开；设过期时间，定期复查与轮换。

---

## 一句话总结

`Metadata` 人人都要，但真正决定风险的是**写权限落在哪一组**：落在第一组能删库，落在第三组能改 CI，落在第五组能把真实漏洞标成误报。配令牌时不要按「这个脚本好像会用到」来勾，按「它最少必须要哪几项」来勾。
